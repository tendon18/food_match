# FoodMatch
## 1. サービス概要

FoodMatchは、複数人での食事で「どこでもいい」と話が止まってしまう問題を解決するサービス。

参加者それぞれが予算・ジャンル・エリア・避けたい条件などを入力し、候補店舗を持ち寄ることで、全員の条件に合いやすい店舗を比較・整理できる。

「誰か一人がお店を探して調整する」のではなく、みんなの条件をもとに納得できるお店を決めやすくすることを目指す。

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

友人と食事に行くとき、「どこ行く？」と聞いても「どこでもいい」と返ってくることが多く、結局自分が候補を探すことがあった。

候補を出しても、「そこは少し遠い」「予算は大丈夫？」など後から条件が出てきて、また別のお店を探すことも多い。

そのたびに「みんなで食事を楽しみたいのに、お店を決めることが負担になっている」と感じたことが、FoodMatchを考えたきっかけになる。

### 2-2. なぜそれが「気になった」のか

自分自身、友人との食事では全員が気持ちよく過ごせる場所を決めたいと考える一方、一人だけが条件を整理して調整する状況に負担を感じていた。

「なんでもいい」という言葉の裏にも、予算や苦手なもの、場所など、言葉にしていない条件があるのではないかと考えたことから、この問題を解決したいと思った。

自分自身がFoodMatchを使いたい理由：
- 毎回一人でお店を探す負担を減らしたい。
- 後から予算や苦手なものが出てくる状況を減らしたい。
- お店探しではなく、友人との時間を楽しむことに集中したい。

## 3. 課題の整理

### 3-1. 表に見えている困りごと

複数人で食事をするとき、お店を決めるためのやり取りが長くなり、一人に負担が集中しやすい。

### 3-2. 本当に解決したい課題

なぜ？：
- お店を決めるために、参加者それぞれの希望を確認する必要があるから。
- 予算やジャンル、場所などの条件が最初から整理されていないから。
- 「なんでもいい」と言いながらも、それぞれに言葉にしていない条件があるから。

本当に解決したい課題：
- 複数人で食事をするとき、それぞれの条件を整理して共有する負担が大きく、納得できるお店を決めにくいこと。

### 5-3. 差別化を「体験価値」で表現する

食べログなどで「お店を探す」のではなく、普段使っているサービスで見つけた候補を持ち寄り、FoodMatchで「みんなで決める」ことを支援する。

気持ちの変化：
- 「また自分が決めないといけない」という負担を減らし、友人との食事をもっと気軽に決められる。

考え方の変化：
- 「なんでもいい＝何も条件がない」ではなく、それぞれに言葉にしていない条件があるかもしれないと考えられるようになる。

### 6-2. 価値を一文で表す

FoodMatchは、複数人での食事で「どこでもいい」と話が止まってしまう人たちが、みんなの条件を整理して、納得できるお店を決めやすくするサービス。

### 6-3. FoodMatchの利用シナリオ

4人(A,B,C,D)で金曜日に食事をする場合：

これまでは
- Aが「どこ行く？」と聞く。
- B,C,Dが「どこでもいい」と返ってくる。
- Aが候補を探す。
- B,C,Dから「そこは遠い」「予算は大丈夫？」と言われる。
- 別の候補を探す。
- 後から条件が出てきて、なかなか決まらない。

FoodMatchを使った場合：
- Aがグループを作ってURLを共有。
- 4人(A,B,C,D)がそれぞれ条件を入力。
- 各自が気になる店舗を追加。
- FoodMatchが条件を照らし合わせてランキング
- おすすめ理由を確認。
- 参加者が納得した店舗を決定。

結果：一人に調整を任せる負担を減らし、条件を整理したうえで短時間に決めやすくなる。

## 7. このアプリで実現すること
### 7-1. MVPでの一連の体験

「複数人の条件を集める → 候補を持ち寄る → 条件に合う店舗を比較する」という一連の体験を検証する。

特に以下の3つを中心に実装する。

- 条件入力：参加者それぞれの条件を集める。
- 候補店舗の追加：参加者全員が候補を持ち寄る。
- 店舗のスコアリング：集めた条件と店舗を照らし合わせる。

### 7-2. MVPで作る機能
### ① グループ作成・共有

食事に行くメンバー用のグループを作成する。

グループ参加用のURLを発行し、LINEなどで共有する。
参加者はURLからグループに参加する。

### ② 参加入力

参加者が以下の条件を入力する。

- 予算
- 希望ジャンル
- エリア
- 避けたい条件

条件は「必須条件」と「希望条件」に分けて扱う。
入力項目を増やしすぎず、短時間で入力できることを重視する。

### ③ 候補店舗の追加

参加者全員が候補店舗を追加する。
Instagram・食べログ・Googleマップなどで見つけた店舗を持ち寄る形を想定する。

店舗登録時に以下を必須項目とする。

必須項目
- 店舗名
- 予算
- ジャンル
- エリア

任意項目
- 特徴
- 店舗URL
- メモ

5項目すべてを必須にすると、4人が2店舗ずつ追加した場合、合計40項目の入力が必要になる。
そのため、MVPでは店舗名・予算・ジャンル・エリアの4項目に絞る。

特徴などの追加情報は、入力された場合のみスコアリングに利用する。
情報が入力されていない場合は、推測で判定せず「情報不足」として扱う。

MVPでは、店舗情報を完全に登録することよりも、「参加者それぞれが候補を持ち寄り、複数人の条件を比較してお店を決める」というFoodMatchの中心的な体験を検証することを優先する。

店舗情報の自動取得や詳細情報の補完は、本リリース後に対応する。

### ④ 店舗のスコアリング：

参加者の条件を「必須条件」と「希望条件」に分けて、店舗を評価する。

### ⑤ 必須条件と希望条件の分け方
FoodMatchでは、すべての条件を同じように扱うのではなく、「絶対に避けたい条件」と「できれば満たしてほしい条件」を分けて評価する。

・必須条件：満たさない店舗は候補から除外する。
・希望条件：満たすほど加点し、満たさない場合や条件から離れるほど減点する。

MVPでは以下のように扱う。

| 条件 | 扱い | 判定方法 |
|------|------------|------------|
| 避けたい条件・NG条件 | 必須条件 | 該当する店舗は除外 |
| 予算 | 希望条件 | 予算内なら加点、予算を越えるほど減点 |
| 希望ジャンル | 希望条件 | 希望ジャンルと一致すれば加点 |
| エリア・駅からの距離 | 希望条件 | 希望するエリアや駅から近いほど加点 |

予算は「必須条件」ではなく「希望条件」とする。

予算を超えた店舗も候補として残す。
ただし、予算を超えるほど減点が大きくなり、予算内の店舗が上位になりやすくする。

「予算を少し超えるが、ジャンルや場所の条件には非常によく合う店舗」も候補として残し、最終的な判断は参加者自身が行えるようにする。

### ⑥ スコアリングの考え方
まず、必須条件を確認する。

1. 参加者のNG条件に該当する店舗を除外する。
2. 必須条件を満たした店舗について、希望条件を評価する。
3. 予算・ジャンル・エリアなどの一致度に応じて加点・減点する。
4. 合計スコアの高い順にランキングする。
5. スコアだけでなく、どの条件が評価に影響したのかも表示する。

### ⑦ スコアリング例
4人の参加者が以下の条件を入力したとする。

- A：予算3,000円、イタリアン希望
- B：予算2,500円、イタリアン希望
- C：予算3,000円、駅から近い店希望
- D：予算2,000円、辛いものを避けたい

候補店舗として、以下の3店舗が追加されたとする。

| 店舗 | 予算 | ジャンル | エリア | 特徴 |
|------|------------|------|------|------|
| イタリアンA店	| 2,500円 | イタリアン | 駅から徒歩5分 | 辛い料理なし |
| イタリアンB店	| 3,500円 | イタリアン	| 駅から徒歩10分 | 辛い料理あり |
| 和食C店 | 2,000円 | 和食 | 駅から徒歩3分 | 辛い料理なし |

### ⑧ 必須条件を確認する

- イタリアンA店：辛い料理なし → 必須条件を満たすため候補に残る。
- イタリアンB店：辛い料理あり → Dの「辛いものを避けたい」という必須条件に該当するため除外。
- 和食C店：辛い料理なし → 必須条件を満たすため候補に残る。

この時点で、イタリアンB店はランキング対象から除外される。

### ⑨ 希望条件で残った店舗を評価する
残ったイタリアンA店と和食C店について、予算・ジャンル・エリアを評価する。

**イタリアンA店**
- Aの希望ジャンル「イタリアン」に一致。
- Bの希望ジャンル「イタリアン」に一致。
- Cの「駅から近い」という希望に一致。
- Aの予算3,000円以内。
- Bの予算2,500円以内。
- Dの予算2,000円を500円超過するため、Dの予算条件では減点。
- DのNG条件「辛いものを避けたい」は満たしている。

**和食C店**
- Aの希望ジャンル「イタリアン」とは一致しない。
- Bの希望ジャンル「イタリアン」とは一致しない。
- Cの「駅から近い」という希望に一致。
- A・B・C・Dの予算以内。
- DのNG条件「辛いものを避けたい」は満たしている。

この例では、イタリアンA店はDの予算を500円超えているが、予算は希望条件であるため候補からは除外しない。

一方で、A・Bの希望ジャンルとCの希望するエリアに一致しているため、予算超過による減点を受けながらも高いスコアになる可能性がある。

逆に和食C店は4人全員の予算内であるものの、A・Bの希望ジャンルには一致しない。

このように、FoodMatchでは「全員の条件を完全に満たす店舗」を無理に1つ選ぶのではなく、必須条件を満たした店舗の中から、参加者全体の希望条件への一致度を比較する。

### ⑩ おすすめ理由の表示

ランキングだけでなく、店舗ごとにスコアに影響した理由も表示する。

例：
- 4人中2人が希望するジャンルと一致
- 4人中3人の予算以内
- Dの予算を500円超過しているため減点
- 駅から徒歩5分以内
- 避けたい条件に該当しない

など、店舗ごとの評価理由を表示する。

これにより、単に「1位だからおすすめ」とするのではなく、「なぜこの店舗が上位なのか」を参加者全員が確認できるようにする。

最終的な店舗の決定はFoodMatchが行うのではなく、表示されたランキングやおすすめ理由を参考に、参加者自身が行う。

### ⑪ おすすめランキング

全員の条件に合いやすい順に店舗を表示する。

### 本リリースで作る機能
- 店舗情報の自動取得。
- 店舗候補の検索。
- 履歴を保存・確認する。
- Gemini APIを使ったおすすめ理由の文章生成。
- 条件入力をもっと簡単にするUI。

MVPでは、参加者の条件をもとに店舗を評価してランキングするところまで作る。
本リリースでは、そこに店舗の検索や情報の自動取得を追加する。さらにGemini APIを使って、「なぜこのお店がおすすめなのか」を分かりやすく説明する。

アレルギーについて：
- アレルギー情報は、店舗の安全性を判定する条件としては使用しない。
- 店舗情報だけでは、調理環境や最新のアレルギー対応状況まで正確に判断できないため。
- そのため、MVPではアレルギーに関する情報を「避けたい条件」として記録できる場合でも、店舗が安全であるとは判定しない。
- アレルギーへの対応が必要な場合は、利用者自身が店舗へ確認することを推奨する。

## 8. このアプリの懸念点とその対策

### 懸念点①：条件入力が面倒になる

- 何が問題になりそうか：
条件入力や候補店舗の登録が面倒で、FoodMatchを使わなくなる可能性がある。
- なぜそう思うか：
「ご飯について考える気分じゃない」「お店選びが面倒」という声があり、入力項目が増えると本来減らしたい負担を増やしてしまうため。
- そのために考えている対策：
参加者の条件は「絶対に避けたい」「できれば希望したい」など、少ない入力から始められるようにする。

また、候補店舗の登録についても、MVPでは店舗名・予算・ジャンル・エリアの4項目のみを必須とし、特徴などは任意入力とする。

情報が入力されていない項目については推測で補完せず、「情報不足」として扱うことで、入力の手間とスコアリングの精度のバランスを取る。

### 懸念点②：候補店舗がない

- 何が問題になりそうか：比較する候補がなければスコアリングできない。
- なぜそう思うか：FoodMatchは「お店を探す」より「お店を決める」ことを解決したいが、候補がなければ決めることもできないため。
- そのために考えている対策：MVPではInstagram・食べログ・Googleマップなどで見つけた店舗を参加者全員が持ち寄る。
将来的には店舗情報を取得して候補を出せるようにし、「お店を探すこと」自体の負担にも対応する。

### 懸念点③：アレルギー対応を誤解される

- 何が問題になりそうか：
FoodMatchのスコアリング結果を見て、「この店舗ならアレルギーがあっても安全に食事できる」と誤解される可能性がある。
- なぜそう思うか：
店舗情報だけでは、調理環境や食材の混入、最新のアレルギー対応状況などをFoodMatch側で正確に判断できないため。
- そのために考えている対策：
MVPでは、アレルギー情報を店舗の安全性を判定する条件として使用しない。

アレルギーに関する情報が入力された場合でも、「この店舗なら安全」とは判定せず、必要に応じて利用者自身が店舗へ確認するよう注意書きを表示する。

FoodMatchでは、アレルギーの安全性を保証するのではなく、あくまで店舗選びの条件を整理するための補助情報として扱う。

## 9. 今後の展開・発展の方向性

FoodMatchは「一度お店を決めたら終わり」ではなく、使った結果を次回のお店選びにも活かせるサービスを目指す。
毎回細かく入力するのではなく、「前回と同じ条件で探す」など、少ない操作で使えるようにする。

### 観点

ユーザーはなぜ使い続ける？：
- 友人や職場の人と食事をするたびに利用でき、使うほどお店を決める負担を減らせるため。
続けることで何が変わる？：
- 過去の条件や選択結果を活用することで、毎回一から条件を入力する必要がなくなり、少ない操作でお店を決められるようになる。
データが溜まると何ができる？：
- 過去に選んだ店舗・条件・満足度などを蓄積し、グループごとの好みや傾向をおすすめに活用できる。

### 今考えている発展案

機能追加の方向性：
- 履歴を分析・おすすめに活用する。
- グループごとの好みや傾向の記録。
- 過去の満足度や選択結果を使ったおすすめ。
- 選択履歴を使った候補の絞り込み。
- 「前回と同じ条件で探す」機能。
- 店舗ページやSNSなどへのリンク共有。

UI・体験の改善：
- 過去の条件を再利用したり、候補の比較やおすすめ理由の確認を簡単にしたりすることで、お店を決めるまでの操作を減らす。

機能以外の工夫：
- FoodMatchが「お店を探すサービス」ではなく、「みんなで納得してお店を決めるサービス」として定着することを目指す。
- 最終的な決定はFoodMatchが行うのではなく、参加者自身が納得して決められることを大切にする。

### 10-2. 技術選定の比較検討

| Node.js / Express | 不採用 | カリキュラムで学習していないため、MVPでは学習コストが高くなる |

| MongoDB | 不採用 | MVPでは学習コストが高くなる |

| Hotwire（Turbo & Stimulus） | 採用 | ページ全体を再読み込みせず、条件入力やスコアリング結果などを部分的に更新できるため。カリキュラムで学習済み |
| JavaScript | 採用 | Hotwire（Stimulus）の実装に使用。カリキュラムで学習済み |
| React / Next.js | 不採用 | MVPではReactのキャッチアップまで含めると開発の負担が大きくなるため。本リリース後にキャッチアップし、FoodMatchへ組み込むメリットがあるか検証する |

### 認証機能
| 候補 | 採用/不採用 | 理由 |
|------|------------|------|
| Sorcery | 採用 | FoodMatchのMVPでは高度な認証機能よりもサービスの核となるスコアリング機能の実装を優先したいため。カリキュラムで学習済みの技術でシンプルに実装できる |

今回チャレンジしたい点：
- 複数人の条件を扱うDB設計。
- ユーザー・グループ・候補店舗などのリレーション設計。
- 店舗ごとのスコアリングロジック。
- 必須条件と希望条件を分けた判定。
- 共有URLを使ったグループ参加。
- おすすめ理由を表示する仕組み。

特に、単純なCRUDアプリで終わらず、入力された条件から店舗を評価する部分にチャレンジする。

不安な点：
- 複数人の条件を組み合わせるため、データ設計やスコアリングが複雑になりすぎる可能性がある。
- そのためMVPでは、予算・ジャンル・エリア・NG条件などに絞って実装し、最初から完璧な条件を作らない。

### 10-3. キャッチアップ不足の懸念

新しい技術をMVPから増やしすぎると、キャッチアップに時間がかかり、FoodMatchの主要機能の完成が遅れる可能性がある。
そのためMVPでは、学習済みのRails・PostgreSQL・Renderを中心に、

条件入力 → スコアリング → ランキング → おすすめ理由

までをルールベースで完成させる。

React・Next.jsは本リリース後に必要性を検証し、必要に応じて導入する。

Gemini APIは本リリースで導入するが、店舗選びやスコアリングまでAIに任せる予定はない。
そこは自分でルールを決めて実装し、Gemini APIには「なぜこのお店がおすすめなのか」を分かりやすく伝えてもらう役割を持たせる。
