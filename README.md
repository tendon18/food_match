# FoodMatch
## 1. サービス概要

FoodMatchは、複数人での食事で「どこでもいい」と話が止まってしまう問題を解決するサービス。

参加者それぞれが予算・ジャンル・エリア・避けたい条件などを入力し、候補店舗を持ち寄ることで、全員の条件に合いやすい店舗を比較・整理できる。

「誰か一人がお店を探して調整する」のではなく、みんなの条件をもとに納得できるお店を決めやすくすることを目指す。

## 2. このアイデアはどこから生まれたか

### 2-1. きっかけとなった体験・感情

友人と食事に行くとき、「どこ行く？」と聞いても「どこでもいい」と返ってくることが多く、結局自分が候補を探すことがあった。

候補を出しても、「そこは少し遠い」「予算は大丈夫？」など後から条件が出てきて、また別のお店を探すことも多い。

そのたびに「みんなで食事を楽しみたいのに、お店を決めることが負担になっている」と感じたことが、FoodMatchを考えたきっかけになる。

### 2-2. なぜそれが「気になった」のか

自分自身、友人との食事では全員が気持ちよく過ごせる場所を決めたいと考える一方、一人だけが条件を整理して調整する状況に負担を感じていた。

「なんでもいい」という言葉の裏にも、予算や苦手なもの、場所など、言葉にしていない条件があるのではないかと考えたことから、この問題を解決したいと思った。

- 自分自身がFoodMatchを使いたい理由
 毎回一人でお店を探す負担を減らしたい
 後から予算や苦手なものが出てくる状況を減らしたい
 お店探しではなく、友人との時間を楽しむことに集中したい

## 3. 課題の整理

### 3-1. 表に見えている困りごと

複数人で食事をするとき、お店を決めるためのやり取りが長くなり、一人に負担が集中しやすい。

### 3-2. 本当に解決したい課題

- なぜ？
 お店を決めるために、参加者それぞれの希望を確認する必要があるから。
 予算やジャンル、場所などの条件が最初から整理されていないから。
 「なんでもいい」と言いながらも、それぞれに言葉にしていない条件があるから。

- 本当に解決したい課題
 複数人で食事をするとき、それぞれの条件を整理して共有する負担が大きく、納得できるお店を決めにくいこと。

## 4. 想定ユーザーについて

### 4-1. 想定しているユーザー

年齢設定：
  - 年齢：20代前半
  - 理由：友人や職場の人など複数人で食事をする機会があり、LINEなどで日常的に予定を調整しているため。

生活・状況：
  - 生活・状況：友人4〜5人程度で食事に行く際、お店選びを一人に任せたり、グループチャットで相談したりしている人。
  - 理由：複数人の希望をまとめる場面で、FoodMatchの価値を最も感じてもらいやすい。

環境設定：
  - 環境：スマートフォンでLINEなどを使って予定を決めている環境。
  - 理由：共有URLを送るだけで参加できるため、アプリのインストールや複雑な登録を必要とせず利用できる。

### 4-2. 自分とユーザーの距離

- 自分自身
 実際に友人との食事で、お店を探して調整する負担を感じた経験があり、自分自身が最初のユーザーとして想像しやすいため。

### 4-3. 実際に使われる可能性について(需要・存在確認)

- まず最初に使ってくれそうな人は誰か？
 最初に使ってくれそうなのは、友人との食事で毎回お店を決める人や、グループで「どこに行く？」というやり取りが長くなりがちな人。

- その人は、どんな場面でこのアプリを思い出すか？
 食事の予定が決まったタイミングでFoodMatchを思い出し、LINEで共有URLを送って利用する。

- 今の生活の中で、代わりに使っているものは何か？/それを置き換えてまで使う理由はあるか？
 現在はLINEで相談したり、食べログ・Googleマップなどで候補を探したりしているが、Foodateではそれらを置き換えるのではなく、候補を持ち寄って最後に決める部分を支援する。

### 4-4. ユーザーがサービスを導入して利用するまでのイメージ(導入・継続の流れ)

1. 食事の予定が決まる
2. 幹事がFoodateでグループを作成
3. 共有URLをLINEなどで送る
4. 参加者が各自の条件を入力
5. 気になる店舗を候補として追加
6. Foodateが条件を照らし合わせてランキング
7. おすすめ理由を確認し、参加者が店舗を決定
8. なぜこの流れが現実的なのか
9. 共有URLを送るだけなので、アプリのインストールが不要
10. 各自が空いた時間に条件を入力でき、LINEで返信を待つ必要がない
11. 候補店舗を全員で持ち寄るため、一人だけがお店を探す負担を減らせる

利用を続ける理由として、将来的には過去の条件や選択結果を活用し、「前回と同じ条件で探す」など少ない操作で利用できるようにする。

### 5-2. それでも自分が作りたい理由

既存サービスには「探す」「保存する」「ランダムに決める」ための機能がある一方、複数人の条件をまとめて、お店を決める部分はあまり解決されていないと感じた。

自分自身が友人との食事で感じてきた「お店を決める負担」を減らし、友人との時間をもっと気軽に楽しめるようにしたい。

### 5-3. 差別化を「体験価値」で表現する

FoodMatchは、「複数人の条件がバラバラな状態から、みんなが納得できる候補を短時間で整理できる」体験を提供する。

食べログなどで「お店を探す」のではなく、普段使っているサービスで見つけた候補を持ち寄り、FoodMatchで「みんなで決める」ことを支援する。

## 6. このサービスで提供したい価値

### 6-1. ユーザーの変化

- 行動の変化：「誰かが候補を探して、みんなに聞いて、また候補を探す」というやり取りを減らせる。
- 気持ちの変化：「また自分が決めないといけない」という負担を減らし、友人との食事をもっと気軽に決められる。
- 考え方の変化：「なんでもいい＝何も条件がない」ではなく、それぞれに言葉にしていない条件があるかもしれないと考えられるようになる。

### 6-2. 価値を一文で表す

FoodMatchは、複数人での食事で「どこでもいい」と話が止まってしまう人たちが、みんなの条件を整理して、納得できるお店を決めやすくするサービス。

### 6-3. FoodMatchの利用シナリオ

例えば4人(A,B,C,D)で金曜日に食事をする場合：
これまでは
- Aが「どこ行く？」と聞く。
- B,C,Dが「どこでもいい」と返ってくる。
- Aが候補を探す。
- B,C,Dから「そこは遠い」「予算は大丈夫？」と言われる。
- 別の候補を探す。
- 後から条件が出てきて、なかなか決まらない。

FoodMatchを使った場合：
- Aがグループを作ってURLを共有。
- 4人(A,B,C,D)がそれぞれ条件を入力。
- 各自が気になる店舗を追加。
- FoodMatchが条件を照らし合わせてランキング
- おすすめ理由を確認。
- 参加者が納得した店舗を決定。

結果：一人に調整を任せる負担を減らし、条件を整理したうえで短時間に決めやすくなる。

### 6-4. 長く使うことで得られる価値

将来的には、過去の利用結果を次回のお店選びに活用する。
- 過去に選んだ店舗・条件の履歴
- グループごとの好みや傾向
- 過去の満足度を使ったおすすめ
- 「前回と同じ条件で探す」機能

一度使って終わりではなく、使うほど少ない操作でお店を決められる状態を目指す。

## 7. このアプリで実現すること
 
### MVPで作る機能

「複数人の条件を集める → 候補を持ち寄る → 条件に合う店舗を比較する」

という体験を検証する。

特に以下の3つを中心に実装する。

- 条件入力：参加者それぞれの条件を集める
- 候補店舗の追加：参加者全員が候補を持ち寄る
- 店舗のスコアリング：集めた条件と店舗を照らし合わせる


①グループ作成：食事に行くメンバー用のグループを作成する。

②共有URL：グループ参加用のURLを発行し、LINEなどで共有する。

③条件入力：参加者が予算・ジャンル・エリア・苦手なもの/避けたい条件などを入力する。
入力項目を増やしすぎず、面倒にならないようにする。

④候補店舗の追加：参加者全員が候補店舗を追加する。
　Instagram・食べログ・Googleマップなどで見つけた店舗を持ち寄る形を想定する。
　店舗登録時には、店舗名・予算・ジャンル・エリア・特徴など、スコアリングに必要な情報を入力する。

⑤店舗のスコアリング
例：
4人の参加者が以下の条件を入力したとする。

A：予算3,000円、イタリアン希望
B：予算2,500円、イタリアン希望
C：予算3,000円、駅から近い店希望
D：予算2,000円、辛いものを避けたい

候補店舗として、以下の3店舗が追加されたとする。

店舗	予算	ジャンル	エリア	特徴
イタリアンA店	2,500円	イタリアン	駅から徒歩5分	辛い料理なし
イタリアンB店	3,500円	イタリアン	駅から徒歩10分	辛い料理あり
和食C店	2,000円	和食	駅から徒歩3分	辛い料理なし

スコアリングの流れ
- 必須条件で除外
 イタリアンB店は全員の予算上限を満たさないため除外する。
- 希望条件で順位付け
 イタリアンA店は「4人中2人が希望するジャンル」「駅から徒歩5分以内」など、希望条件との一致度が高い。
- おすすめ理由を表示
 「全員の予算内」「4人中2人が希望するジャンル」「駅から徒歩5分以内」など、なぜおすすめなのかを表示する。

このように、単にランキングを表示するだけでなく、「なぜこの店舗がおすすめなのか」が分かる状態を作る。

※具体的な配点は、実装・検証を通して調整する。

⑥ おすすめランキング

全員の条件に合いやすい順に店舗を表示する。

⑦ おすすめ理由

「なぜこの店舗がおすすめなのか」も表示する。

例：
- 4人全員の予算範囲内
- 4人中3人が希望するジャンル
- 駅から徒歩5分以内
- 避けたい条件に該当しない
最終的な店舗の決定はFoodMatchではなく、参加者自身が行う。

### 本リリースで作る機能
- 店舗情報の自動取得
- 店舗候補の検索
- 過去に利用したグループ・店舗の履歴
- 過去の選択結果を使ったおすすめ
- 選んだお店への満足度記録
- Gemini APIを使ったおすすめ理由の文章生成
- 条件入力をもっと簡単にするUI
- 店舗ページやSNSなどへのリンク共有

アレルギーについて：
- アレルギー情報は、店舗の安全性を判定する条件としては使用しない。
- 店舗情報だけでは、調理環境や最新のアレルギー対応状況まで正確に判断できないため。
- そのため、MVPではアレルギーに関する情報を「避けたい条件」として記録できる場合でも、店舗が安全であるとは判定しない。
- アレルギーへの対応が必要な場合は、利用者自身が店舗へ確認することを推奨する。

AIは店舗の選定そのものを任せるのではなく、ルールベースで計算した結果を分かりやすく伝える補助役として使う。

## 8. このアプリの懸念点とその対策

### 懸念点①：条件入力が面倒になる

- 何が問題になりそうか：条件入力が面倒で、FoodMatchを使わなくなる可能性がある。
- なぜそう思うか：「ご飯について考える気分じゃない」「お店選びが面倒」という声があり、入力が増えると本末転倒になるため。
- そのために考えている対策：「絶対に避けたい」「できれば希望したい」など、少ない入力から始められるようにする。候補店舗も参加者全員が追加できるようにする。

### 懸念点②：候補店舗がない

- 何が問題になりそうか：比較する候補がなければスコアリングできない。
- なぜそう思うか：FoodMatchは「お店を探す」より「お店を決める」ことを解決したいが、候補がなければ決めることもできないため。
- そのために考えている対策：MVPではInstagram・食べログ・Googleマップなどで見つけた店舗を参加者全員が持ち寄る。
将来的には店舗情報を取得して候補を出せるようにし、「お店を探すこと」自体の負担にも対応する。

### 懸念点③：アレルギー対応を誤解される

- 何が問題になりそうか：FoodMatchのランキング結果を見て、「この店舗ならアレルギーに対応している」と誤解される可能性がある。
- なぜそう思うか：店舗情報だけでは、調理環境や最新のアレルギー対応状況まで正確に判断できないため。
- そのために考えている対策：アレルギーについては店舗の安全性を保証するものではないことを明確に表示する。
アレルギーへの対応が必要な場合は、利用者自身が店舗へ確認することを推奨する。

### 10-2. 技術選定の比較検討

### バックエンド
| 候補 | 採用/不採用 | 理由 |
|------|------------|------|

| Node.js / Express | 不採用 | カリキュラムで学習していないため、MVPでは学習コストが高くなる |

### データベース
| 候補 | 採用/不採用 | 理由 |
|------|------------|------|

| MySQL | 不採用 | PostgreSQLで十分対応可能なため |
| MongoDB | 不採用 | MVPでは学習コストが高くなる |

### フロントエンド
| 候補 | 採用/不採用 | 理由 |
|------|------------|------|

| Hotwire（Turbo & Stimulus） | 採用 | ページ全体を再読み込みせず、条件入力やスコアリング結果などを部分的に更新できるため。カリキュラムで学習済み |

| React / Next.js | 不採用 | MVPではReactのキャッチアップまで含めると開発の負担が大きくなるため。本リリース後にキャッチアップし、Foodateへ組み込むメリットがあるか検証する |

- 今回チャレンジしたい点：
・複数人の条件を扱うDB設計
・ユーザー・グループ・候補店舗などのリレーション設計
・店舗ごとのスコアリングロジック
・必須条件と希望条件を分けた判定
・共有URLを使ったグループ参加
・おすすめ理由を表示する仕組み

特に、単純なCRUDアプリで終わらず、入力された条件から店舗を評価する部分にチャレンジする。

- 不安な点：

複数人の条件を組み合わせるため、データ設計やスコアリングが複雑になりすぎる可能性がある。
そのためMVPでは、予算・ジャンル・エリア・NG条件などに絞って実装し、最初から完璧な条件を作らない。

### 10-3. キャッチアップ不足の懸念

新しい技術をMVPから増やしすぎると、キャッチアップに時間がかかり、Foodateの主要機能の完成が遅れる可能性がある。
そのためMVPでは、学習済みのRails・PostgreSQL・Renderを中心に、

条件入力 → スコアリング → ランキング → おすすめ理由

までをルールベースで完成させる。
React・Next.jsやGemini APIは本リリース後に必要性を検証し、必要に応じて導入する。
